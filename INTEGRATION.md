## Конфликты и принятые решения

Git merge не выполнялся: сервер извлечён выборочно из `origin/main`.
Текстовых merge-конфликтов нет. Обнаруженные смысловые конфликты:

1. **Структура.** Настоящая ветка уже содержит `frontend/`. Она сохранена;
   рядом добавлен `backend/` со своей Python-средой и Dockerfile.
2. **Старый UI.** Исключён `main/web/**`, включая его зависимости, дизайн,
   тесты, сборку и сценарии записи. Убрана отдача `web/dist` из Flask.
   Серверный runtime больше не собирает и не копирует старый frontend.
3. **Авторизация.** По дополнительному запросу пользователя добавлены email/пароль
   и регистрация вместо серверного доверия `x-user-id`. Пароль хранится как
   scrypt-хеш Werkzeug, токен сессии — только как SHA-256-хеш; cookie — HttpOnly,
   SameSite=Strict, восемь часов. Токен ротируется при входе и отзывается при выходе.
   CSRF-токен хранится только в памяти клиента; проверяются Origin и CSRF.
   Вход ограничивается по IP и email. Старый вход не принимает новые portal-аккаунты.
4. **Роли.** Публичная регистрация создаёт только `intern`. `mentor` и `lead`
   создаются административной CLI, права проверяются сервером, запросы ограничены
   командой. Роль исходного пользователя в legacy-таблице не заменяется
   фронтендовой ролью: роль портала хранится отдельно.
5. **Контракт.** Новые endpoints соответствуют `frontend/src/services/index.ts`
   и `frontend/src/api/schemas.ts`. Форматы и пути исходного API сохранены.
   Отгулы, черновики, согласование и пользовательские запросы реализованы сервером,
   поскольку эквивалента в `main` не было. Состояние хранится в PostgreSQL.
6. **Каталоги.** Нет надёжного соответствия 17 пунктов frontend и расширенного
   каталога main. Для сохранения интерфейса используется отдельный серверный
   каталог и его прогресс. Чат читает именно этот прогресс; поиск знаний и AI
   используют серверные модули из main. Совместимость не выдаётся за единый каталог.
7. **Статус доступа.** `approved` исходного main не означает выдачу. В новом
   API статус frontend `approved` возвращается после локальной записи выдачи.
   Подключение реального провайдера выдачи требует замены демо-операции.
8. **Конфиги и порты.** Корневые Compose/README/env добавлены заново: в ветке
   frontend их в корне нет. Существующие `frontend/compose.yaml`, Dockerfile,
   nginx.conf и vite.config.ts сохранены. Интеграционные конфиги добавлены отдельно.
   Один origin, `/api` через proxy, Vite 5173, nginx 8080, API 5050; MSW выключен.
9. **Зависимости.** package.json и package-lock.json frontend сохранены.
   Python-зависимости ставятся в backend/.venv; исходный конфликт имён
   `server/` и `ai/server.py` учитывается отдельными запусками AI-тестов.
10. **Проверки.** Старый агрегатор покрытия main/web и сценарий генерации
    фикстур из отсутствующих исходных XLSX исключены. Серверные проверки,
    контрактные примеры, AI-evals и проверка покрытия каталога сохранены.
    `.gitattributes` фиксирует LF для серверных текстовых файлов: исходные байты
    миграций и их контрольные суммы не зависят от Windows autocrlf.

## Изменения существующего frontend

Разрешённое пользователем исключение для настоящего входа:

- `src/pages/LoginPage.tsx`: формы входа/регистрации; старый mock-вход сохранён;
- `src/stores/auth.ts`: серверная сессия и выход, без localStorage в реальном режиме;

Остальные исходные файлы frontend, включая все страницы, кроме входа,
UI-компоненты, стили, справочники, схемы, сервисы, исходные тесты и npm-манифесты,

`Dockerfile.integrated`, `nginx.integrated.conf`, `vite.integrated.config.ts`.

## Ограничения исходного интерфейса

Справочники синтетические. В исходных формах остаются тексты с именами
демо-наставников и описание имитационного чата; экраны сохранены по требованию.
Каталог frontend содержит заранее заданные сроки. Метрики без измеренной базы
возвращают нули; `internsOnTrackShare` отражает долю стажёров с выполненными пунктами.
Публичное подтверждение email, сброс пароля и внешние HR/IAM-интеграции не реализованы.

## Ручная проверка

1. Зарегистрировать новый email; проверить короткий пароль, повторный email и
   невозможность передать роль `lead` в запросе регистрации.
2. Войти с верным/неверным паролем. Перезагрузить страницу: сессия восстанавливается.
   Выйти: старый cookie больше не авторизует. Пароля/сессии нет в localStorage.
3. Открыть главную, таймлайн, контакты, базу знаний, метрики, чат и формы; проверить
   мобильную ширину и переключение темы. В Network запросы идут в API, не MSW.
4. Пройти пункт без согласования. Пункт с согласованием отправить наставнику;
   стажёр не может подтвердить его прямым API-запросом.
5. Создать отгул, доступ и черновик. Отправить черновик, перезагрузить страницу,
   перезапустить сервер: записи сохраняются. Другой стажёр не видит чужие заявки.
6. Создать mentor/lead через CLI и войти. Проверить команду, очередь пунктов,
   согласование заявки до выдачи и отказ с комментарием. Повторное согласование
   закрытой заявки возвращает 409 и не создаёт вторую выдачу.
7. Проверить чат: следующий шаг и прогресс совпадают с таймлайном, формы доступны
   по карточкам действий. Неизвестный вопрос не создаёт заявку автоматически.
8. Проверить 400 для неверного JSON, 401 для истёкшего cookie, 403 для чужой роли
   и неверного CSRF/Origin, 409 для повторного перехода, 429 при переборе входа,
   сетевую ошибку при остановке API. В live AI проверить 503 при отказе провайдера.
