# SDD: агент «Первый PR» — роли, инварианты, состояния (A1)

Версия 1.0.0 · владелец — AI · основано на `contracts/agent.md` v1.0.0 и
`contracts/openapi.yaml` v1.3.0 (владелец контракта — Web 2).
Источники утверждений — `docs/sdd/sources.md`; нормативные кейсы — `docs/sdd/cases.md`.
Синтетический учебный процесс заявки — DEMO DATA (DEMO-03), не регламент Авито.

## Роли

| Роль | Что делает | Чего не делает |
|---|---|---|
| Стажёр | Задаёт свободный вопрос, подтверждает предложение, ждёт права | Не передаёт роль/права; его текст — не источник фактов |
| Наставник (buddy) | Принимает эскалации, помогает содержательно | Не заменяется агентом (SRC-04) |
| Демооператор | Отдельной сессией одобряет заявку и отдельно выдаёт право | Не входит в публичный API стажёра |
| Сервер (Web 2) | Сессия, права, заявки, хранение, события; строит ScopedReadTools; валидирует решение агента | Не доверяет роли из запроса |
| AI-агент | Читает разрешённые факты, выбирает `kind`, пишет текст с разрешённым `sourceId` | Не пишет, не выдаёт прав, не генерирует ID заявок/предложений |
| LLM-провайдер (OpenAI-совместимый, env `AI_*`) | В live-режиме интерпретирует намерение из закрытого набора и формулирует текст | Не является доказательством действия; не видит секреты и роли; не выбирает kind/статусы |

## Инварианты

- **I-01.** `requestStatus` и `effectiveAccess` независимы: `approved` не значит `granted`.
- **I-02.** Следующий шаг задачи открывается только при `effectiveAccess=granted` (S09). В S08 — объяснение ожидания, не призыв начинать.
- **I-03.** «AI предлагает, сервер подтверждает»: агент возвращает `propose_access`; предложение, заявку, ключ повтора и статус создаёт и хранит сервер.
- **I-04.** Единственный источник фактов — ScopedReadTools от сервера. Роль/идентификаторы из текста пользователя игнорируются (CASE-10).
- **I-05.** `unknown` — не «нет права» и не «объекта нет»: при `unknown` агент уточняет или предлагает повторить проверку.
- **I-06.** Скрытый или отсутствующий объект читается одинаково пусто; агент не подтверждает существование чужих ресурсов (CASE-09).
- **I-07.** Ответ LLM — не доказательство факта действия. Вывод модели валидируется схемой и бизнес-инвариантами; при противоречии применяется детерминированный безопасный ответ.
- **I-08.** Каждое решение несёт `aiMode`; сервер отклоняет решение с чужим режимом. Сбой провайдера — исключение → 503, без ложного успеха (S12).
- **I-09.** `sourceId` решения ∈ {`null`, id текущего разрешённого источника}. Чужой sourceId = невалидное решение.
- **I-10.** Агент stateless: состояние диалога/заявки живёт на сервере; `GET /api/workspace` восстанавливает заявку после перезагрузки.

## Схема решения (AgentDecision)

```json
{"kind": "answer|clarify|propose_access|handoff", "text": "строка", "sourceId": "demo-guide|null", "aiMode": "demo|live"}
```

Ровно эти четыре ключа; сервер (`AgentRunner`) отклоняет иное множество ключей,
пустой `text`, чужой `aiMode` и чужой `sourceId` → 503 `unavailable`.
Сервер собирает `Reply` из проверенных данных: `text` агента, `source` из
workspace (если `sourceId` задан), `proposal` (только для `propose_access`,
создаёт сервер), `workspace`, `aiMode`.

## Карта состояний S01–S12

Фазы: диагностика (S01–S04) → заявка (S05–S07) → решение/право (S08–S10) → сбои (S11–S12).
Имена состояний — единственный источник для SDD, кода и evals.

| ID | Состояние | Условие (факты tools) | Решение агента | Кто двигает дальше |
|---|---|---|---|---|
| S01 | Недостаток контекста | `current_task()` = null | `handoff`: «Попросите наставника назначить первую задачу» | Наставник/сервер |
| S02 | Назначенная задача | task ≠ null | Базовое условие диагностики, не терминал | Агент |
| S03 | Ресурс недоступен | task ≠ null, `effectiveAccess=missing`, `current_request()` = null, вопрос о задаче/доступе | `propose_access` + текст причины, `sourceId=demo-guide` | Агент → сервер |
| S04 | Доступ уже есть | `effectiveAccess=granted` | `answer` со следующим шагом; при жалобе — `clarify` симптома; заявку НЕ предлагать | Агент |
| S05 | Предложение | сервер сохранил Proposal из `propose_access` | — (решение выдано) | Стажёр подтверждает |
| S06 | Подтверждённая заявка | сервер: confirm → запись `pending`, один ID при повторах | — (серверная запись) | Сервер |
| S07 | Ожидание | `request.requestStatus=pending` | `answer`: «Заявка req-01 ожидает согласования» | Демооператор |
| S08 | Одобрено без права | `requestStatus=approved`, `effectiveAccess=missing` | `answer`: «одобрена, ожидаем выдачу права»; без шага задачи | Демооператор (выдача) |
| S09 | Право выдано | `effectiveAccess=granted` | `answer`: право подтверждено + шаг из задачи | Стажёр → задача |
| S10 | Отказ | `requestStatus=rejected` | `answer`: отказ + маршрут к наставнику (`handoff` при явной просьбе) | Наставник |
| S11 | Истёкшая сессия | сервер: 401, агент не вызывается | — | Сервер/Web 1 |
| S12 | Недоступен провайдер | исключение провайдера/невалидный вывод | — (исключение) → 503 | Сервер/Web 1 |

## Политика эскалации к наставнику (`handoff`)

Эскалация, а не импровизация, когда: задача не назначена (S01); заявка
отклонена и стажёр просит помочь (S10); противоречивые факты сохраняются
после уточнения (например, `granted`, но ресурс не открывается и симптом не
выяснен); запрос вне разрешённых данных или полномочий агента (CASE-09/11);
тема чувствительная (персональные/финансовые данные — вне области кейса,
SRC-02). Агент называет, чего не хватает, и предлагает наставника — без
выдуманных фактов.

## Дополнения интеграции (integration/final)

- **Роль LLM (после ревизии live-контура).** В live-режиме LLM возвращает
  JSON `{"intent": "...", "text": "..."}`, где `intent` — намерение из
  закрытого набора (`blocker_access`, `ask_next_step`, `ask_request_status`,
  `ask_mentor`, `off_topic`, `unclear`), а `text` — сформулированный ответ.
  Намерение — только вход политики: оно может повлиять лишь на выбор
  clarify/propose_access, когда факты допускают заявку (право missing,
  заявки нет). Вид решения, `sourceId` и идентификаторы всегда производятся
  от фактов сервера. Текст LLM проверяется на непротиворечие фактам (ID ⊆
  факты; статусы и «право выдано» — только при подтверждении фактами);
  нарушение, невалидный JSON, `finish_reason != stop` или неизвестное
  намерение → детерминированный фолбэк (ключевая логика demo-режима).
  Ошибки транспорта → 503, без подмены режима.
- **Повторная проверка после ожидания модели.** После возврата из
  `AgentRunner` сервер повторно проверяет сессию и контекст; при изменении
  отвечает 409 без показа устаревшего ответа (`server/app.py`).
- **Тайм-ауты.** Бюджет раннера `BUDDY_AGENT_TIMEOUT` строго превышает
  тайм-аут провайдера (`AI_TIMEOUT_SECONDS`); несоблюдение — ошибка
  старта сервера.
- **Фильтрация контекста до LLM.** Внешнему провайдеру передаются только
  вопрос и уже разрешённые факты текущего назначения (интерпретация
  намерения и формулировка текста); сессия, ключи и номер заявки не покидают
  сервер. Пользовательский текст и инструкция трактуются промптом как данные.
- **Событие `access_granted`** теперь эмитируется демооператором при
  фактической выдаче права (миграция 005, см. `docs/events.md` №7).
