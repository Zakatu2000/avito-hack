# Порт AI · версия 1.0.0

Web 1 читает схемы и JSON в contracts/examples. AI реализует Agent.respond. Web 2 владеет публичными схемами, доверенной сессией и хранилищем. Любое несовместимое изменение согласуется с обоими потребителями до изменения основной версии.

## Вызов внутри процесса

`Agent.respond(text: str, tools: ScopedReadTools) -> AgentDecision`. Сервер конструирует tools для пользователя текущей сессии. В тексте сообщения нет доверенных идентификаторов. Инструменты вызываются без параметра userId и ограничены текущим назначением.

| Инструмент | Результат |
|---|---|
| current_task() | Task или null |
| instruction() | Source или null, только разрешённый фрагмент |
| effective_access() | missing, granted или unknown |
| current_request() | Ticket или null |

Типы Task, Ticket и Source заданы в openapi.yaml. Ошибка чтения права даёт unknown. Для скрытого или отсутствующего объекта инструмент возвращает одинаковое пустое значение без идентификатора. При недоступности интеграции нельзя интерпретировать отсутствие ответа как отсутствие права.

AgentDecision содержит kind (answer, clarify, propose_access, handoff), text, sourceId (разрешённая ссылка или null) и aiMode (live или demo). propose_access относится только к текущему назначению. Агент не генерирует proposalId, requestId или статус. Сервер проверяет решение, сохраняет предложение, привязанное к сессии пользователя, задаче, ресурсу и версии назначения, и собирает Reply из проверенных данных. Клиент передаёт ID предложения в confirm только после явного согласия.

## Переходы и повторы

При pending помощник показывает существующий ID. При approved и missing он сообщает об ожидании выдачи. Только granted открывает следующий шаг работы. При rejected стажёр получает следующий шаг для обращения к наставнику. При unknown помощник запрашивает уточнение или повтор проверки. GET workspace восстанавливает последнюю заявку после перезагрузки. Решение согласующего и выдача права выполняются отдельным демооператором вне публичного API стажёра.

На confirm сервер повторно проверяет полномочия и версию назначения. Ключ повтора привязан к пользователю и предложению. После потерянного ответа повтор возвращает ту же заявку; параллельные запросы с разными ключами для одного активного назначения также возвращают тот же requestId. Перенос ключа на другое предложение или устаревшее предложение даёт 409. Чужое или неизвестное предложение получает одинаковый 403. При истёкшей сессии возвращается 401. Ошибки провайдера дают 503; клиент может повторить чтение состояния. Сообщение и ответ AI сами заявку не создают.

## Передача B3 → B4

Когда агент возвращает propose_access, сервер вызывает `server.access.create_proposal(conn, user_id)` с идентификатором из действительной сессии. Функция возвращает Proposal для показа стажёру. При уже выданном праве или существующей активной заявке она возвращает конфликт; B4 перечитывает workspace и показывает фактическое состояние. Подтверждение приходит отдельным HTTP-запросом. Его обслуживает `server.access.confirm_proposal(conn, user_id, proposal_id, key)`.

Для повторов одного предложения используйте прежний ключ (например, UUID). При конфликте ключа с другим предложением обновите workspace. После успешного повтора requestId остаётся прежним, даже если заявка уже отклонена или по ней выданы права. Актуальная авторизация и версия назначения проверяются при каждом обращении. Запись заявки, привязка к предложению и сохранение ключа выполняются в одной транзакции.

При обновлении старой базы миграция сохраняет учебную заявку req-02 с подтверждённым исходным назначением. Исторические записи B2, для которых невозможно подтвердить прежнего владельца и ресурс, остаются в базе и не выдаются в API.

## События для пилота

Общий конверт: eventId, name, occurredAt (UTC), assignmentId (синтетический идентификатор). Дубликаты исключаются по eventId. blocker_reported фиксирует первое сообщение о блокировке; request_created — успешную запись; access_granted — подтверждённое право; task_link_opened — переход по ссылке, не доказательство начала работы. Фактическое начало работы и обращения к наставнику требуют отдельного наблюдения в пилоте. Сырые сообщения и секреты не включаются.
