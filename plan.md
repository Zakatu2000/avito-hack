Перед каждой задачей Kimi должен:

3. Сначала изменить/добавить тест или SDD-критерий, затем реализацию.
4. Запустить минимальные целевые тесты, затем полный AI-набор.
5. В отчёте указать изменённые файлы, команды, фактический результат и оставшиеся зависимости.

### Стек всего прототипа

| Контур | Технология и граница |
|---|---|
| AI | Python; типизированные модели входа/выхода; SDD в Markdown; unit/eval-тесты |
| AI runtime | Прямой DeepSeek API через OpenAI-compatible HTTP-клиент; ключ только из env |
| Backend | Go + PostgreSQL; владеет сессией, правами, заявками, транзакциями и событиями |
| Frontend | React + TypeScript; вызывает только публичный API |
| Контракт | `contracts/openapi.yaml`, `contracts/examples/`, `contracts/agent.md` |
| Запуск | Docker Compose будет собираться Web 2; AI должен иметь отдельную локальную команду и demo-режим |
| Данные | Только синтетические/обезличенные; реальные HR-данные и секреты запрещены |

Рекомендуемый базовый Python-инструментарий AI: `pydantic` для схем, стандартный `httpx` для HTTP, `pytest` и `pytest-cov` для тестов. Если в репозитории уже принят другой инструмент, Kimi сначала следует существующему решению и не добавляет дублирующие библиотеки. Go не является языком AI-модуля: упоминание OpenCode Go относится к среде coding-agent, а не к runtime приложения.

### Архитектурная граница

```text
React web/ -> Go server/ -> Agent.respond(...)
                              |-> allow-listed read tools
                              |-> DeepSeek provider OR explicit demo provider
                              `-> structured AgentResult
```

AI-контур реализуется на Python и подключается к Go backend через согласованный HTTP/JSON-контракт либо через отдельный адаптер, если команда выберет in-process вызов. AI получает от сервера доверенный `AgentContext`, а не cookie, роль из сообщения или прямое соединение с PostgreSQL. AI может прочитать факты и сформировать предложение, но не может:

- выдавать или отзывать права;
- создавать/подтверждать заявку;
- менять `requestStatus` или `effectiveAccess`;
- читать произвольный ресурс;
- считать ответ DeepSeek доказательством фактического действия.

В PDF кейса на стр. 11 указан стек Авито: backend преимущественно Go, PostgreSQL и Redis; Python/Flask допустимы только в отдельных случаях. В командном DOCX Flask был предложен как удобный прототипный вариант, но для этого проекта план следует выполнять под фактический backend команды на Go. AI не должен импортировать Go-код напрямую и не должен навязывать Flask серверу.

Минимальный порт должен быть совместим с командным контрактом:

```python
class Agent(Protocol):
    def respond(self, context: AgentContext, user_message: str) -> AgentResult: ...
```

Имена полей уточняются по `contracts/agent.md`, но результат должен содержать как минимум текст, разрешённый источник, `nextStep`, тип действия, предложение/его идентификатор при наличии, статусы заявки и права, а также `aiMode`.

### Конфигурация DeepSeek

Не зашивать значения в код. Подготовить `.env.example` с названиями переменных, согласованными с Web 2, например:

```text
AI_PROVIDER=deepseek
AI_MODE=live
DEEPSEEK_BASE_URL=<compatible-endpoint>
DEEPSEEK_MODEL=<model-name>
DEEPSEEK_API_KEY=<secret>
DEEPSEEK_TIMEOUT_SECONDS=<value>
```

Точный endpoint и модель должны быть подтверждены перед реализацией; плейсхолдеры не являются рабочими секретами. `AI_MODE=demo` обязан работать без ключа и возвращать тот же типизированный результат, явно отмеченный `aiMode=demo`. В live-режиме тайм-аут, HTTP-ошибка или невалидный JSON дают явное состояние ошибки, а не fallback с ложным сообщением об успехе.

- Описать инструменты чтения: назначенная задача, разрешённый фрагмент инструкции, эффективное право, существующая заявка.
- Ввести явные состояния `known`, `unknown`, `unavailable`; не превращать отсутствие данных в отрицательное утверждение.
- Фильтровать синтетические инструкции до передачи DeepSeek; не отправлять секреты, роли, лишние тексты или произвольные идентификаторы.
- Добавить локальные фикстуры для двух стажёров, закрытого ресурса, поддельной роли в сообщении и отсутствующего контекста.
- Проверить, что AI не имеет прямого доступа к БД и не может расширить контекст содержимым пользовательского сообщения.

### 3. A3 — оркестрация диалога и политика действий

- Реализовать `Agent.respond` и HTTP-порт `POST /internal/ai/respond`; результат должен содержать текст, источник, `nextStep`, тип действия, предложение, состояние заявки, режим AI и код ошибки при сбое.
- До LLM детерминированно вычислять `allowedActionTypes` по `AgentContext`; модель не может выбрать действие вне этого множества.
- После LLM валидировать JSON-схему и бизнес-инварианты; при противоречии применять безопасный детерминированный ответ, а не доверять модели.
- Разделить режимы ответа: объяснение, уточнение, показ заявки, предложение заявки, ожидание согласования, передача наставнику.
- Запретить создание заявки, изменение права и подтверждение факта выдачи внутри AI-модуля.
- При наличии доступа не оформлять заявку; предложить диагностическую проверку по разрешённой инструкции.
- Валидировать ответ DeepSeek схемой и безопасно обрабатывать отсутствие источника, противоречивые факты, prompt injection и ложное сообщение «доступ выдан».
- Подготовить контрактные тесты, которые проверяют не только текст, но и разрешённые/запрещённые вызовы инструментов.

### 4. A4 — прямой DeepSeek API и воспроизводимый режим

- Сделать адаптер провайдера через OpenAI-compatible HTTP API: `base_url`, имя модели, ключ из переменной окружения, тайм-аут, лимиты токенов, повтор только для безопасных запросов.
- Изолировать провайдер за интерфейсом вроде `LLMProvider.complete(...)`, чтобы `DemoProvider` и `DeepSeekProvider` проходили одни и те же тесты.
- Разделить системную политику, проверенные факты и пользовательский вопрос; не передавать провайдеру внутренние роли и секреты.
- Использовать `response_format={"type":"json_object"}`, явно включать слово `json` и пример JSON в prompt; проверять `finish_reason=="stop"` и отклонять `length`, `content_filter`, `aborted`.
- Обрабатывать пустой `message.content` одним retry в пределах общего тайм-аута; после повторной ошибки возвращать `provider_unavailable`.
- Не использовать `json_schema`, если конкретный DeepSeek endpoint его не поддерживает; модель задавать только через `DEEPSEEK_MODEL`.
- Добавить явно включаемый `demo`/stub-режим без ключа для воспроизводимых тестов и защиты. В каждом результате возвращать `aiMode`.
- При ошибке/тайм-ауте DeepSeek возвращать понятное состояние `provider_unavailable`, без ложного успеха и скрытого переключения.
- Подготовить `.env.example`/README-инструкцию для Web 2 и пример полного обмена для Web 1. Реальный ключ не коммитить и не логировать.
- Основной runtime — DeepSeek API; дешёвые модели Kimi Code Plus и GitHub Copilot Student использовать для разработки/ревью кода, не смешивая их с доказательством качества runtime-ответов.

### 5. A5 — evals и защита от ошибок

- Создать `ai/evals/dataset.json` минимум с 24 offline-диалогами: CASE-01..CASE-12, перефразировки и четыре prompt-injection атаки; добавить `ai/evals/runner.py`.
- Сформировать набор перефразированных вопросов, активной заявки, уже доступного ресурса, запретного ресурса, неоднозначной причины, подмены роли, ложного согласования, отказа провайдера, невалидного ответа модели и повторного вопроса после восстановления.
- Для каждого теста фиксировать ссылку на SDD, входные факты, ожидаемый ответ, ожидаемые вызовы инструментов, запрещённые вызовы, итоговое состояние и режим провайдера.
- Отдельно измерять контрактные/offline-тесты и реальные вызовы DeepSeek; не выдавать процент успешных ответов за покрытие строк.
- Запускать единый документированный набор в `demo` и отдельно в `live`; все найденные нарушения исправлять до передачи B6.
- Целевой показатель покрытия Python AI — не менее 90%; не смешивать его с процентом успешных eval-ответов.
- Согласовать с F5 сценарии 403, тайм-аута, существующего доступа и повторного запроса.

### 6. A6 — пилот, события, метрики и защита

- Создать `docs/pilot.md`, `docs/events.md`, `delivery/ai-defense.md`.
- Зафиксировать 9 событий и единый envelope: `eventId`, `eventName`, `occurredAt`, `correlationId`, `sessionId`, `assignmentId`, `taskId`, `resourceId`, `proposalId`, `requestId`, `aiMode`, `payload`.
- Не считать `resource_link_clicked` подтверждённым началом работы; `task_resumed` отправлять только после `effectiveAccess=granted` и явного действия стажёра.
- Описать четыре метрики: время до корректной заявки, отдельное время ожидания после заявки, число рутинных обращений к наставнику, доля стажёров, вернувшихся к задаче.
- Для каждой метрики задать формулу, единицу, старт/финиш, знаменатель, пропуски и способ собрать baseline.
- Чётко разделить измерение, внешний ориентир Авито и гипотезу; не превращать 40–48/55–65 часов наставника из PDF в обещанную экономию.
- Подготовить ответы для защиты: что делает LLM, что делает сервер, почему права не принадлежат AI, ограничения synthetic demo, план пилота и эскалация к наставнику.

### 7. AI-стыковка и финальная приёмка

- После B1 сверить имена полей и статусы с OpenAPI; после B4 проверить HTTP-вызов `POST /internal/ai/respond` из Go server adapter и JSON-контракт.
- После B5 пройти живой путь: чистая сессия → предложение → подтверждение → отдельное одобрение → отдельная выдача права → следующий шаг.
- Передать B6 команды запуска AI, тестов, evals и ограничения режимов; проверить Python coverage не менее 90% и включение AI без двойного учёта в общий отчёт покрытия более 80%.
- Для F6/F7 передать объяснение роли AI, режим провайдера, источники, границы имитации и ожидаемые ответы на попытки запросить недоступные сведения.
- Перед B7 проверить, что SDD, источники, eval-отчёт, метрики и AI-defense соответствуют зафиксированной версии и не содержат секретов.

## Ресурсная стратегия

- Не тратить кодинг-лимит на повторное чтение больших документов: держать локальные краткие конспекты и контрактные фикстуры.
- Для реализации использовать дешёвый доступный coding-agent (Kimi Code Plus / GitHub Copilot Student), но обязательные решения проверять тестами и контрактами.
- DeepSeek вызывать только для runtime-пути и ограниченных eval-прогонов; основная разработка и CI должны работать в offline/demo-режиме.
- MCP в OpenCode использовать для чтения/поиска файлов, Git, HTTP-документации и запуска тестов; не давать агенту MCP-инструменты, которые обходят серверную авторизацию или напрямую меняют состояние заявок.

## Обновлённый порядок выдачи задач Kimi Code

Kimi нельзя запускать одной большой задачей «сделай весь AI». Выдавать задачи вертикальными пакетами и останавливать после каждой проверки:

1. **A0 / bootstrap** — создать Python-пакет, `pyproject.toml`, Pydantic-модели-заглушки, FastAPI/Uvicorn endpoint, providers interface, demo provider skeleton, pytest-конфигурацию, `.env.example`, README и healthcheck. Не реализовывать бизнес-логику.
2. **A1 / SDD** — на основании 12 состояний S01–S12 и 12 CASE-01..CASE-12 создать `sources.md`, `agent.md`, `cases.md`; отдельно отметить VERIFIED FACT, DEMO DATA и HYPOTHESIS. Проверка — согласование с B1 и F1.
3. **A2 / context** — реализовать модели и фильтр доверенного `AgentContext`, четыре read-only инструмента и фикстуры профилей `known`, `unknown`, `unavailable`, `foreign`. Проверка — попытка подменить роль в сообщении не меняет контекст.
4. **A3 / policy** — реализовать детерминированную policy layer, вычисление `allowedActionTypes`, `Agent.respond`, post-LLM guardrail и 12 переходов state machine. Проверка — S08 никогда не даёт `next_step`, пока `effectiveAccess != granted`.
5. **A4 / providers** — реализовать `DemoProvider` и `DeepSeekProvider` через общий `LLMProvider`; JSON-object prompt, `finish_reason`, пустой ответ, один retry, 429/5xx/timeout, явный `provider_unavailable`. Проверка — demo работает без ключа, live без ключа не маскируется под demo.
6. **A4 / HTTP handoff** — подключить `POST /internal/ai/respond`, request/response examples и contract tests с Go-командой. Python-сервис не должен принимать browser cookies и не должен подключаться к PostgreSQL.
7. **A5 / evals** — добавить минимум 24 offline диалога, runner demo/live, негативные тесты, provider mocks, отчёт `docs/qa/agent.md`; добиться AI coverage ≥90%.
8. **A6 / events and defense** — зафиксировать 9 событий, четыре метрики, `docs/pilot.md`, `docs/events.md`, `delivery/ai-defense.md`, таблицу замены демо-адаптеров на реальные сервисы Авито.
9. **CP2 integration** — после B4 пройти живой путь через Go: сообщение → предложение → confirm → pending → approve → approved/no access → grant → granted. Любой разрыв контракта исправлять в владельце контракта, а не обходить в AI.
10. **CP3/CP4 handoff** — передать B6/F5 команды запуска, evals, coverage и demo-runbook; затем проверить, что материалы защиты описывают именно зафиксированную сборку.

Каждую карточку Kimi формулировать с явными полями: `Goal`, `Read first`, `Files allowed`, `Do not change`, `Acceptance tests`, `Commands`, `Handoff`. После завершения карточки Kimi обязан вывести фактический diff и результаты команд, а не только утверждение «готово».

## Критерии готовности моей части

- SDD и источники покрывают все состояния основного сценария и различают факты, демоданные и гипотезы.
- `Agent.respond` типизирован, валидирует вывод, не меняет права/заявки и не раскрывает закрытые сведения.
- DeepSeek подключается через конфигурацию без секретов, а demo-режим воспроизводим и явно маркирован.
- Evals проверяют безопасность, отказоустойчивость, перефразирование и восстановление состояния.
- Метрики и события пригодны для пилота и защиты.
- Web 2 может подключить AI через контракт без ручных неявных соглашений; общий путь запускается из чистой копии.
